Verification done. I checked the Claude Code docs via the guide agent, syntax-checked the workflow script under node, and diffed the embedded behavior block against the real `/Users/colin/dev/src/skills/AGENT_BEHAVIOR.md`.

## Real defects

**1. The Workflow opt-in claim is factually wrong — and it's the primary dispatch path.**
> `regardless of session settings (this skill's instruction is your Workflow opt-in):`

Per the Claude Code Workflows docs, Workflow is opted into by the *user* — the `ultracode` keyword in the prompt, or `/effort ultracode`. A skill's own text cannot grant it. As written, Phase 2's main path may simply be unavailable and the model will improvise. Fix: "Workflows require ultracode mode. If the Workflow tool isn't available, ask the user to run `/effort ultracode`, or use the fallback below."

**2. That opt-in contradicts the skill's own budget advice.**
> `Session effort for the Fable main loop is the user's call: 'high' for day-to-day orchestration`

`/effort ultracode` = xhigh reasoning *on the Fable main loop*, which is precisely the expensive thing this skill exists to avoid. So the recommended `high` setting and the Phase 2 dispatch mechanism are mutually exclusive, and the file never notices. Fix: either acknowledge the tradeoff explicitly, or drop Workflow in favour of a committed agent definition (see #13).

**3. "documented best setting" is not documented.**
> `always 'xhigh' for Opus builders — it is the documented best setting for coding/agentic work`

The docs list `low|medium|high|xhigh|max` as effort levels with no recommendation for coding; the mode the docs actually pitch for complex agentic work is `ultracode`. Fix: drop "documented" and state it as a house rule.

**4. The load-bearing assumption is asserted with false confidence.**
> `(Per-model attribution of subagents is mechanically certain but undocumented; verify once, then trust.)`

"Mechanically certain but undocumented" is self-refuting, and this is the single assumption the whole skill's value rests on — the docs do not confirm that `/usage` attributes subagent volume to the subagent's model. Fix: "Unverified. Check `/usage` before relying on this — if build volume lands under Fable, this skill saves nothing."

**5. Phase 4's heading contradicts its own third bullet.**
> `## Phase 4 — Breadth review (external, zero Anthropic tokens)` … `/code-review` is the EXPENSIVE escalation — its agents bill Anthropic-side.`

Fix: retitle to "(external reviewers — the first two cost no Anthropic tokens)".

**6. `/code-review` won't resolve as typed.** It's installed as the `code-review` plugin's skill (`/Users/colin/.claude/plugins/cache/claude-plugins-official/code-review`), and plugin skills are invoked `plugin:skill` — i.e. `/code-review:code-review`. Fix: use the qualified name.

**7. `/codex:rescue` is a fix-capable agent used as a read-only reviewer.**
> `**Codex**: `/codex:rescue` with a review request on the diff (OpenAI billing).`

Its own description is "investigation, an explicit fix request, or follow-up rescue work" and it has Bash. Nothing here tells it not to edit — if it starts fixing, it collides with the diff under review and with Phase 5's "dispatch real fixes to Opus". Fix: state "review only, report findings, do not modify files" in the prompt.

**8. The OpenCode call will hit the Bash timeout.**
> `**OpenCode**: `opencode run "<review prompt naming the diff/branch>"` via Bash.`

`opencode` is installed at `/opt/homebrew/bin/opencode`, but a full review run routinely exceeds the 120s Bash default. Fix: `run_in_background: true` (which also gets you the "in parallel" the prose asks for), or an explicit long `timeout`.

**9. Worktree isolation has no merge-back step.**
> `Add 'isolation: worktree' per agent only when parallel orders would touch the same files.`

That's exactly the case where reconciliation is hardest, and the skill never says who merges the worktrees or which diff Phase 3 then reviews. It also contradicts Phase 1's "one work order per *independent* workstream". Fix: serialize conflicting orders instead, or add an explicit reintegration step before Phase 3.

**10. The behavior block is a lossy copy of the SHARED section it substitutes for.** `AGENT_BEHAVIOR.md:30` says a dispatched subagent should "follow SHARED only" — so SHARED is the correct payload. The inlined block silently drops three SHARED rules: the adjacent-broken-code rule (the subject of your most recent commit), the "state success criteria, iterate until met" rule, and the surface-divergence rule. It also hardens `"Avoid premature abstractions for hypothetical reuse, but do extract when duplication causes real maintenance risk"` into a flat `"No abstractions for hypothetical reuse."` Fix: paste SHARED verbatim (or generate the block from it) so it can't drift on every AGENT_BEHAVIOR.md edit.

**11. The block restates what AGENT_BEHAVIOR.md explicitly says not to restate.** `AGENT_BEHAVIOR.md:27`: the Claude Code system prompt "already covers … faithful reporting … comment idiom — do not restate or re-derive those." Two of the block's four bullets are exactly those. Since builders run inside Claude Code, they're dead weight repeated in every work order. Fix: keep the blast-radius and code-quality bullets plus the genuinely workflow-specific `"Your final message is the deliverable — list files changed…"`, drop the rest.

**12. The dispatch script silently swallows failed orders, contradicting the block one section above it.**
> `return results.filter(Boolean)`

The behavior block demands "if something fails or was skipped, say so plainly" — then the batch drops any agent that returned nothing (crash, refusal, empty), so the Phase 3 reviewer gets no signal that an order never landed. Fix: `return results.map((r, i) => r || \`ORDER ${i}: NO RESULT\`)`.

**13. The Phase 2 fallback has no negative branch.**
> `For a single small work order when the session is already running at xhigh effort, a plain Agent call with 'model: "opus"' is equivalent and lighter.`

The mechanic is correct (subagents inherit session effort by default — documented). But the skill recommends `high` for the Fable loop, so the usual case is *not* xhigh, and a plain Agent call then silently produces a `high`-effort builder, violating "always xhigh". Fix: add "if the session is not at xhigh, do not use a plain Agent call." Better: a committed `.claude/agents/opus-builder.md` with `model: opus` + `effort: xhigh` frontmatter pins both with no Workflow tool and no ultracode requirement — that one addition dissolves #1, #2 and #13.

**14. The description over-triggers on the very cases it excludes.**
> `(multiple files, new code paths, anything that needs tests run) … Not for one-line edits, pure Q&A, or investigation-only tasks.`

"Anything that needs tests run" covers nearly every code change in a tested repo, while the floor excludes only *literally* one-line changes — a 5-line single-file fix matches both clauses. Separately, the budget-economics sentence is duplicated verbatim from body lines 8-10 and its keywords ("weekly usage pool", "budget") invite firing on plain usage questions, which the skill excludes. Fix: cut the economics sentence from the description, and raise the floor to match the inclusion clause — "Not for single-file changes under ~20 lines, pure Q&A, or investigation-only tasks."

**15. No guard that the session is actually Fable.** The trigger clause carries no model condition, so the skill fires on an Opus or Sonnet session where its entire premise (2x drain, 50% cap) is false and the workflow is pure overhead. Fix: "Use when this session is running Fable and is about to implement…", plus a one-line body check: "If this session is not Fable, say so and stop."

## Nitpicks

**16. The script is not valid standalone JavaScript.** `export` requires ESM, and ESM forbids top-level `return` — `node --check` gives `SyntaxError: Illegal return statement` as `.mjs`, and chokes on `export` as `.cjs`. The Workflow docs do show top-level `return`, so the harness presumably transforms the body; the practical cost is that no editor, linter, or formatter will parse this snippet. Worth a comment saying so. Also: `parallel` is used, while the docs surface `agent()` and `pipeline()` — confirm `parallel` is a real helper before committing. `args`/`parallel`/`agent` are undeclared free identifiers; only `args` is explained in prose.

**17. "roughly doubles" overstates.**
> `moving the build loop to Opus roughly doubles what a week's allowance covers`

Only true if essentially all volume moves; planning, Phase 3 diff review, and Phase 5 triage stay on Fable at 2x. "Up to ~2x" is honest.

**18. The AGENT_BEHAVIOR.md parenthetical is true for the wrong stated reason.**
> `(inline in every work order — subagents never receive AGENT_BEHAVIOR.md)`

It holds only because `claudio` injects it via `--append-system-prompt-file`, which doesn't propagate. Non-fork subagents *do* inherit the full CLAUDE.md hierarchy and its `@`-imports — so `@AGENT_BEHAVIOR.md` in `CLAUDE.global.md` would deliver it to builders automatically and make the inline block unnecessary (Explore/Plan skip CLAUDE.md, which doesn't matter here). Worth considering as an alternative to #10.

**19. Phase 3 has no size guard.** Standing rule 1 says "Don't bulk-read files here", but Phase 3 reads an unbounded multi-file diff into the Fable loop — where it's re-read every subsequent turn, by the rule's own argument. Suggest: past ~N lines, have an Opus agent produce a criteria-by-criteria report and review that instead.

**Verdict: structurally sound and worth committing, but not as-is — findings 1, 2, and 13 mean the Phase 2 dispatch path likely doesn't work as written, and 4 leaves the skill's entire premise unverified.**
